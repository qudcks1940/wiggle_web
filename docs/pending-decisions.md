# Wiggle Web 미결정 항목

> 마지막 갱신: 2026-08-30
> 이 문서는 아직 사용자의 최종 선택이 필요한 항목을 보존한다. 다음 작업자는 아래 내용을 임의로 확정하거나 구현하지 않는다.

## P-001 학생을 실제로 구분하는 운영 방식

### 현재 문제

- 같은 학급에서 비슷하거나 같은 별명이 생기면 교사가 실제 학생을 구분하기 어렵다.
- 입장 순서로 자동 학생 번호를 붙이는 방식은 출석번호와 관계가 없으므로 사용하지 않기로 했다.

### 현재 합의

- 우선 교사가 학생 프로필을 확인할 수 있는 화면만 만든다.
- 실명·출석번호·명부 연결 방식은 실제 사용자의 의견을 들은 뒤 결정한다.

### 아직 결정하지 않은 것

- 교사가 명부와 익명 프로필을 직접 연결할지
- 학생이 출석번호를 입력할지
- 교사가 개인 QR을 미리 발급할지
- 학급 안에서 별명만 강제로 고유하게 만들지

### 법적 검토 메모 (2026-08-31, 사용자 질문에 대한 분석 — 법률 자문 아님)

사용자 질문 원문: "학급 반 번호를 입력하게 해서 아이들을 판단하려고 하는데 법적으로 문제가 없을려나"

- 반 번호는 단독으로는 식별 불가하지만, 개인정보보호법의 개인정보 정의는
  **"다른 정보와 쉽게 결합하여 알아볼 수 있는 정보"**를 포함한다.
  이 기능의 목적 자체가 교사가 명부와 결합해 아이를 특정하는 것이므로
  "서버에 학교명이 없으니 익명"이라는 방어가 약하다.
- 초등 1~3학년은 전원 **만 14세 미만**이다. 개인정보 처리로 판정되면
  법정대리인 동의 + 동의 확인 절차가 필요해질 가능성이 높고,
  "설치·가입·동의서 없이 수업 코드로 시작"이라는 제품 포지션이 무너진다.
  개인정보처리방침의 "학생은 익명으로 참여" 문장도 거짓이 된다.
- 개인정보보호위원회는 아동 데이터에 엄격한 해석을 적용하는 추세다.
- **결론: 현장 검증(P-005) 전에 결정하지 않는다.** 검증 항목에
  "교사가 실제로 학생 구분에 곤란을 겪는가"가 이미 있다(PRD §9.4).
  검증 후에도 필요하면 도입 전 개인정보 전문 검토를 받는다.
- 중간 경로: 교사가 종이 명부에 `여우화가 = 12번`을 적는 방식은
  서버가 아무것도 수집하지 않아 법적 변화가 없다. 1차 검증에서는 이걸 안내한다.

### 추가 질문 (2026-09-07 — 이름까지 수집하는 안)

사용자 질문 원문: "반 번호 이름으로 수집해서 진행하기로 했어, 법적으로 문제가 없는건가?
선생님한테 물어보니까 학기초에 개인정보제공동의서를 받는다고하는데, 흠 괜찮을려나?"

분석 (법률 자문 아님):

- 이름+반 번호는 결합 논쟁 없이 개인정보다. 만 14세 미만이므로 법정대리인 동의가 필요하고,
  아이 본인·교사 동의로 대체할 수 없다(개인정보보호법 22조의2).
- 학기초 동의서가 유효하려면 문면에 ①수집 항목(이름·반·번호) ②목적(외부 교육 서비스
  이용/위탁) ③제공받는 자(운영 주체 업체명) ④보유 기간이 실제로 있어야 한다.
  학교 자체 목적으로 받은 동의의 전용은 목적 외 이용이다. **동의서 실물 확인 전에는
  "괜찮다"고 판단하지 않는다.** 검증처 3곳(학교 2·지역아동센터)마다 각각 확인해야 한다.
- 동의가 유효해도 서버에 이름이 저장되는 순간 서비스가 개인정보처리자(또는 수탁자)가 되어
  처리방침 개정·안전조치·유출 통지·위탁계약 의무가 생기고, 랜딩 문구
  "학생 이메일·실명 없이 안전하게"와 제품 불변 원칙(실명 금지)을 뒤집게 된다.
- 유지 권고: 위의 중간 경로(교사 오프라인 명부 매핑 `토끼화가 = 3반 12번`)로 1차 검증을
  진행하고, 그래도 부족하면 동의서 실물 + 개인정보 전문 검토를 거쳐 도입을 결정한다.

## P-003 교사 확인 화면 이후의 운영 범위

2026-08-18 읽기 전용 1차 화면에 다음 정보가 구현됐다.

- 동물과 별명
- 프로필 생성 시각과 마지막 활동 시각
- 진행 중·완료 작품 수
- 현재 진행 상태와 최근 작품
- 같은 학급 안의 중복 별명 표시

아직 결정하지 않은 것은 중복 별명을 실제 학생과 연결하는 운영 방식이다. 실명, 출석번호, 교사 메모, 명부 연결 입력란은 운영 방식 결정 전에는 추가하지 않는다.

## P-004 그림책 피드백 루브릭과 실행 정책

### 현재 합의

- 교사는 자기 학급의 완성 그림책을 목록·열람 화면에서 확인한다.
- 개별 또는 체크박스 일괄 피드백 요청을 접수할 수 있다.
- 루브릭이 없을 때는 AI 피드백을 만들지 않고 요청을 `루브릭 대기`로 저장한다.

### 아직 결정하지 않은 것

- 사용자가 제공할 루브릭의 평가 영역, 단계, 문장 형식과 버전 관리 방식
- 한 권당 피드백 길이와 초등학생에게 보여 줄 말투
- 교사가 AI 초안을 검토·수정·승인한 뒤 학생에게 보여 줄지, 교사용으로만 둘지
- 체크박스 일괄 요청의 동시 처리 수와 실패 재시도 정책

## P-005 신규 GitHub 저장소와 Vercel 연결 전환

### 현재 합의

- 이후 개발 코드는 `https://github.com/wwwiggle/new_wiggle`에 push한다.
- 신규 저장소는 `main`을 기본 브랜치로 사용하고 현재 기능 브랜치를 PR로 병합한다.
- 기존 공개 운영 `https://wiggleweb.vercel.app`은 현재 `yonghwan86/wiggle_web`의 `main`과 연결돼 있다.

### 아직 결정하지 않은 것

- Vercel 프로젝트의 Git 저장소 연결을 언제 신규 저장소로 바꿀지
- 기존 저장소를 전환 후 읽기 전용으로 보존할지

## 갱신 규칙

1. 사용자가 항목을 확정하면 결정 내용과 이유를 `product-decisions.md`로 옮긴다.
2. 구현만 끝났다고 제품 결정이 확정된 것으로 보지 않는다.
3. 질문 번호만 기록하지 말고 질문 문장과 선택 결과를 함께 남긴다.
4. 최근 대화와 문서가 충돌하면 사용자의 가장 최근 명시적 지시를 우선하고 문서를 즉시 수정한다.

## P-004 이야기 아크 채택에 따른 학생 홈 구조 (2026-08-30 신설)

### 배경

2026-08-30 학습 과정이 `회차 누적 이야기 아크 → 동화책 1권`으로 교체됐다
(`product-decisions.md`「학습 과정」). 그런데 기존 확정 결정은 그림책을 곁다리로 배치한다.

- PD/학생UI-1: 학생 홈 큰 메뉴 순서는 `이어 그리기 → 내 그림 → 활동 고르기`
- PD/그림책-8: 위 3개 메뉴 순서는 유지하고, 그림책 작업실은 **그 아래 별도 그림책형 카드**로 진입

동화책이 커리큘럼의 종착점이 된 이상, 그림책을 3개 메뉴 아래의 별도 카드로 두는 배치가
여전히 맞는지 확인이 필요하다.

### 아직 결정하지 않은 것

- 학생 홈의 1순위 행동을 `이어 그리기`(그림 단위)로 둘지, `우리 이야기 이어가기`(회차 단위)로 바꿀지
- `활동 고르기`가 회차 아크 안에서 무엇을 의미하는지 (교사가 회차를 정하면 아이의 선택지는 무엇인가)
- 회차 아크 밖의 낱장 그리기를 계속 허용할지, 허용한다면 어디에 두는지
- 동화책 1권이 완성된 뒤 다음 아크로 넘어가는 흐름

### 결정 전까지 하지 않을 것

- 확정 시안 3화면(`examples/*.jpg`)의 재설계 (PD/학생UI-9 유지)
- 학생 홈 메뉴 순서 변경 구현

## P-005 커리큘럼 현장 검증 설계 (2026-08-30 신설)

### 배경

테스트할 학교와 지역아동센터 2곳이 확정됐다. 사용자가 밝힌 최대 우려는
"실제 클라이언트가 쓰지 않는 기능이 많다"와 "교구 안의 커리큘럼이 실제 수업에서 쓰일지 의문"이다.
`docs/ux-market-audit-2026-07.md`에 1~2학년 5명 무개입 사용성 테스트 프로토콜
(과제 6개, 성공 기준: 주요 과제 80% 이상을 중립적 힌트 1회 이하로 완료)이
설계만 되고 실행된 적이 없다.

### 아직 결정하지 않은 것

- 5회차 아크를 두 기관에서 실제로 돌릴지, 아니면 1~2회차만 먼저 검증할지
- 커리큘럼이 "실제로 쓰였다"고 판정하는 기준 (교사가 몇 회차를 스스로 진행했는가 등)
- 검증 대상 학년 (확정 결정은 `초등 3학년 이상`인데 설계 기준은 비문해 저학년 — 아래 P-006 참조)
- 관찰 기록을 제품 안에 남길지 별도 수기로 남길지 (제품 안에 남기면 데이터 수집 원칙 검토 필요)

### 선행 조건 (블로커)

- **구글 OAuth 앱이 미게시라 두 기관 교사가 로그인 자체를 할 수 없다.** 현장 검증 전에 해소해야 한다.

## P-006 핵심 사용자 학년 (2026-08-30 신설)

### 현재 문제

같은 확정 문서 안에서 대상 학년이 갈린다.

- `product-decisions.md`「프로젝트와 제품 중심」6: 핵심 학생 대상은 **초등학교 3학년 이상**
- `CLAUDE.md` 현재 우선순위: **비문해 저학년 독립 사용성**
- 실제 구현 기준(그림 비밀번호 3개, 페이지당 음성 안내 1개, 큰 터치 목표): 글을 못 읽는 아이 기준

3학년 기준이면 현재 온보딩 설계의 상당 부분이 과잉이고,
1~2학년 기준이면 `초등 3학년 이상`이라는 확정 결정을 고쳐야 한다.

### 아직 결정하지 않은 것

- 핵심 사용자 학년을 어디로 확정할지
- 지역아동센터는 학년이 섞이는데 이를 별도 대상으로 볼지
- 두 학년대를 모두 지원한다면 무엇을 학년별로 분기할지
